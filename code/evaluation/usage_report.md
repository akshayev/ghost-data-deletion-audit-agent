## (c) Token-efficiency design

- **Caching keyed on the request.** `llm.chat` keys on provider, purpose, messages and image hash; `llm.tool_chat` keys on messages plus the SHA-256 of the tool schemas (`_tool_cache_key`). A hit never touches the network or the ledger, and works with no API key. An entry made under another model name is reused (`_find_cached`).
- **Batching.** The intake classifier needs 10 batches of up to 40 request texts for 398 unique texts (550 requests), not one call per request.
- **Confidence routing.** Only cases with an open linking decision call the case agent: 252 of 518 full-split cases (48.6%); the other 266 (51.4%) are fully deterministic. Non-deletion requests never enter the agent.
- **Compact tool outputs.** Agent tool results are capped near 900 tokens (`registry._fit`, `MAX_RESULT_CHARS`), the system prompt is about 500 tokens (`prompts/case_agent_system.md`), and the model is told to batch calls in one turn.
- **Only the ambiguity is delegated.** The model decides INCLUDE/EXCLUDE for open points; the planner writes the steps, so output tokens stay small (35,070 completion tokens over 88 cases).
- **Bounded loops.** At most 8 tool calls and 2 rejected proposals per case (`config.yaml` `agent:`), then the deterministic plan is kept.
- **Checkpointing and offline replay.** Finished cases are stored under `code/cache/agent_runs/<config_hash>/`; a rerun, `--no-llm`, or a machine with no keys replays them for free and reproduces the same output.
- **Rate limiting and quota awareness.** `RateLimiter` keeps each model under its requests/min and tokens/min budget, honours `Retry-After`, and retires a model for the run when the provider reports a daily quota.

## (d) Honest notes

- **Wasted intake calls:** 17 real intake calls were made for 10 batches, so **7 were repeats**. Switching Gemini model mid-run (after the daily quota) changed the cache key, so batches already answered were requested again. The cross-model lookup in `llm._find_cached` fixed this.
- **Gemini free tier:** 20 requests per day per model. The 11 screenshot calls and the intake batches exhausted `gemini-3.8-flash`; the remaining batches ran on `gemini-3.5-flash`.
- **Groq free tier:** documented limits are 1,000 requests/day, 8K tokens/minute and 200K tokens/day per model (as given for this event; not re-verified with Groq). The case agent used 468,490 tokens on groq:openai/gpt-oss-120b before the model chain moved on to groq:openai/gpt-oss-20b, groq:qwen/qwen3.8-27b (500,447 tokens so far): consistent with the first model's daily quota ending there, which is the retirement behavior of `llm.tool_chat`. At about 9,226 tokens per routed case, the 252 routed full-split cases need roughly 2,324,952 tokens in total. The 7K tokens/minute client limit also makes the run slow (about one case per 100 seconds), which is why the run is time-boxed.
- **Time-boxed agent run:** the full-split agent runs stopped when the daily quotas were exhausted, before the 15:00 IST time box; the checkpoints were then frozen. Routed cases without an agent answer use the deterministic default (176 cases, `FALLBACK_QUOTA`), and decisions from models that did not pass the sample gate are discarded (37 cases, `FALLBACK_UNVALIDATED_MODEL`): their tokens were spent but do not shape `output.csv`. Gate runs (purpose `case_agent`, sample case ids) are included in (b).
- Costs are estimates from list prices; nothing was billed. No price is configured for groq:qwen/qwen3.8-27b: those rows show "n/a" and are left out of the cost totals (they are connectivity checks).
